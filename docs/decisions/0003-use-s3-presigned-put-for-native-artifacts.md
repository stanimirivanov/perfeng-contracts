# ADR-0003: Use S3 presigned PUT for native artifact upload

- Status: Proposed
- Date: 2026-09-26
- Milestone: M03 — Native Browser Decision Loop
- Deciders: Repository owner
- Supersedes: Artifact-upload authorization aspects of [ADR-0001](0001-native-windows-worker-protocol.md), if accepted
- Superseded by: None

## TL;DR

- Use short-lived S3 Signature Version 4 presigned `PUT` requests for native
  artifact bytes instead of inventing a custom upload gateway.
- Keep object keys server-selected and bind the signature to the exact method,
  key, media type and SHA-256 checksum expected for one attempt and slot.
- Treat the presigned URL and its signed headers as bearer credentials: return
  them only to the authorized worker and never log or persist them.
- Permit an identical upload retry until expiry; artifact registration remains
  the authority that verifies exact stored bytes and makes evidence visible.
- Correct the unreleased candidate Native Worker API v1 contract in a new
  candidate bundle before implementing upload grants in consumers.
- Require live conformance against pinned SeaweedFS as well as AWS-compatible
  semantics before the local vertical slice is accepted.

## Context

The candidate Native Worker API v1 intends browser artifacts to travel directly
from a representative Windows worker to object storage. The control-plane API
must not proxy potentially large traces, profiles or measurement documents, and
the worker must not receive reusable S3 credentials.

The current candidate response instead returns a credential-free
`/upload/runs/...` URL and a custom `X-Perfeng-Upload-Grant` header. An ordinary
S3-compatible endpoint cannot validate that application-specific header. Making
the response executable would therefore require a bespoke public upload gateway
that authenticates the header, enforces object policy and forwards every byte to
S3. That creates another stateful security boundary, service, availability path
and streaming implementation while contradicting the goal of direct upload.

S3 already defines the required delegation primitive. A SigV4 presigned `PUT`
authorizes a time-bounded request for one bucket and key without giving the
caller the signing credentials. AWS documents direct upload through presigned
URLs and warns that the URL is a bearer capability. The pinned SeaweedFS 4.45
source contains SigV4 presigned-request verification, including signed-header
coverage. Provider compatibility still needs a live test because exact checksum
and request-header behavior differs across S3-compatible implementations.

This decision is required before control-plane grant persistence or HTTP code is
added. Otherwise storage and deployment design would silently commit to a
gateway that the accepted protocol did not name or assign to a repository.

## Decision

Native artifact publication will use S3 Signature Version 4 presigned `PUT`
requests generated by the control plane for its configured artifact store. The
worker uploads directly to the externally reachable S3-compatible endpoint; the
Native Worker API process does not receive the artifact body.

For one current native lease, the control plane will:

1. validate the authenticated worker, lease capability, attempt, Run revision
   and requested artifact slot;
2. select the configured bucket and canonical key
   `runs/{runId}/attempts/{attemptId}/{slot}`;
3. verify that size, media type and SHA-256 match the assigned slot constraints;
4. create durable non-secret grant identity and declared-object facts needed by
   later registration;
5. presign only `PUT` for the exact external endpoint, bucket and key, including
   the declared content type and full-object SHA-256 checksum in the signed
   request; and
6. expire the request no later than the current execution lease and the
   deployment's bounded grant lifetime.

The response will carry the complete presigned URL and an explicit closed set of
headers that the worker must reproduce exactly. The URL query contains the
SigV4 signature and is therefore secret bearer material. The separate
`X-Perfeng-Upload-Grant` response header and custom `/upload/runs/...` gateway
URL will be removed from the candidate contract.

The request URL and signed headers are delivery material only. They must not be
stored in PostgreSQL, evidence, fixtures, ordinary logs, metrics or error text.
Persistence keeps only non-secret grant identity, the lease/attempt/slot fence,
canonical object key, declared size, checksum, media type and expiry.

A presigned request can be replayed before expiry. The protocol will describe an
identical retry as safe rather than claim an unenforceable exactly-once write.
The signed checksum prevents a retry from changing the declared payload, and the
attempt-scoped key prevents it from overwriting another attempt. No uploaded
object becomes authoritative merely because S3 accepted it. Artifact
registration must independently inspect and verify the exact object before it
stores an immutable reference.

The signing identity receives only `PutObject` for the reviewed artifact prefix.
It receives no list, read, delete, bucket-management or cross-bucket permission.
The control-plane registration path uses its separately reviewed read access.

### Candidate contract correction

The Native Worker API and bundle are candidates rather than stable releases,
and neither the upload-grant producer nor consumer exists. The next contract
change will therefore correct `native-worker/v1` before its first stable
publication and increment the candidate bundle version. It will update the
OpenAPI response, examples, HTTP cases, rejection cases, documentation and
compatibility notes together. Consumers pinning bundle `0.15.0` by commit must
deliberately move to the corrected bundle; no consumer may mix the old header
shape with the new direct-upload behavior.

If the contract is published as stable before this correction is merged, this
compatibility assumption no longer holds and a new explicit API generation is
required instead of changing v1 in place.

## Alternatives considered

### Keep the custom header and build an upload gateway

- Benefits: Keeps sensitive authorization out of URL query strings and can
  enforce application-specific one-use and byte-count policy before S3.
- Costs and risks: Adds a public streaming service, state sharing, backpressure,
  partial-write recovery, scaling, observability and another deployment path;
  every artifact byte still traverses a Perfeng proxy.
- Reason not selected: The project would reproduce a mature S3 authorization
  mechanism and materially expand M03 operations without demonstrated need.

### Proxy uploads through the Native Worker API

- Benefits: One endpoint and one existing worker authentication mechanism.
- Costs and risks: Couples large evidence transfer to API memory, bandwidth,
  request timeouts and replicas and contradicts ADR-0001's direct-publication
  boundary.
- Reason not selected: Control traffic and artifact data have different scale
  and failure characteristics.

### Give the worker static S3 credentials

- Benefits: Uses unmodified SDK clients and supports retries naturally.
- Costs and risks: Places reusable storage credentials on a laptop and makes
  exact attempt, slot and expiry scoping difficult with the current SeaweedFS
  identity model.
- Reason not selected: The authority is broader and longer-lived than the
  execution lease.

### Issue temporary STS credentials

- Benefits: Uses standardized credentials and can carry a scoped session policy.
- Costs and risks: Requires an STS/IAM integration not enabled by the local
  SeaweedFS deployment, returns multiple reusable credential fields and still
  needs provider-specific compatibility work.
- Reason not selected: Presigning one exact request is smaller and matches the
  single-object workflow.

## Consequences

### Positive

- Artifact bytes travel directly from the native worker to object storage.
- The implementation uses the AWS SDK presigner and the storage provider's
  existing SigV4 verifier instead of a custom authorization service.
- The worker receives no reusable S3 access key or secret key.
- Method, endpoint, bucket, key, content type, checksum and expiry can be bound
  into one reviewed request.
- Attempt-scoped keys and post-upload verification retain the existing
  at-least-once and immutable-evidence model.

### Negative

- The presigned URL is itself secret and its query can leak through careless
  HTTP, proxy, crash or diagnostic logging.
- S3-compatible providers can differ in checksum, signed-header, path-style and
  expiry behavior, so SDK-level unit tests are insufficient.
- A presigned request cannot be individually revoked without expiry or changing
  the signing identity's permissions.
- The local environment needs an externally reachable HTTPS object-store
  endpoint; its current cluster-only HTTP service is insufficient.
- The candidate API response changes and all pinned consumers must update
  together.

### Neutral or follow-up

- `perfeng-contracts` will correct the Native Worker API candidate and document
  the exact signed-header shape.
- `perfeng-control-plane` will add fenced grant persistence and a narrow S3
  presigner adapter; it will not add an artifact upload handler.
- `perfeng-playwright` will upload with the returned URL and exact signed headers
  while redacting the URL from diagnostics.
- `perfeng-environment` will expose a reviewed HTTPS path to SeaweedFS and prove
  it without distributing the signer credentials to the worker.
- `perfeng-k8s` will carry only the signer/read credentials needed by the owning
  workloads and will not place them in worker configuration.

## Compatibility and migration

Candidate bundle `0.15.0` remains an immutable reviewed commit for current
control-plane presence and lease work. The corrected candidate bundle will
change only the not-yet-implemented upload authorization transport; presence,
acquisition, renewal and release semantics remain unchanged.

Control-plane and Playwright consumers must update their pinned contract commit
together before either enables upload grants. There is no persisted upload-grant
data to migrate. Rollback before grant issuance returns both consumers to their
previous pin. After issuance is enabled, rollback waits for the bounded URLs to
expire; no URL or signing material is imported into the old version.

## Security and operations

- Use HTTPS only for the worker-visible object-store endpoint.
- Use a cryptographically authenticated SigV4 request generated by the pinned
  AWS SDK; do not invent a signature format.
- Keep the grant lifetime short and no longer than current lease authority.
- Redact complete presigned URLs, raw query strings and signed headers at every
  logging, metrics, tracing and error boundary.
- Never persist or place live presigned values in fixtures, command arguments or
  GitHub Actions output.
- Scope the signing identity to `PutObject` on the artifact prefix and separate
  it from read, list, delete and bucket-administration identities.
- Treat an accepted upload as untrusted until registration verifies key, size,
  media type and SHA-256 from object storage under the current lease fence.
- Bound the externally reachable ingress and provider request size. If pinned
  SeaweedFS cannot enforce the required signed request or deployment limit, do
  not weaken the contract silently; revisit the gateway alternative in a
  superseding decision.

## Validation

- Verify the corrected OpenAPI document, examples, rejections and HTTP cases
  offline on Windows and Linux.
- Verify that the AWS SDK presigner binds the exact method, external endpoint,
  bucket, key, media type and SHA-256 header without exposing signer credentials.
- Against pinned SeaweedFS, prove successful exact upload and rejection of a
  changed method, path, content type, checksum and expired signature.
- Prove the deployment's upload-size bound and document whether it is enforced
  by the signature, ingress, provider or a reviewed combination.
- Prove an identical retry is harmless and a different payload cannot replace
  the declared object under the same grant.
- Prove the signing identity cannot list, read, delete or write outside the
  reviewed artifact prefix.
- Prove registration rejects absent, oversized, metadata-mismatched or
  checksum-mismatched objects and never treats upload acceptance as evidence.
- Review logs and failure output to confirm that URLs, queries, signed headers
  and long-lived storage credentials are absent.
